# Приёмник событий с очередью обработки

Небольшой сервис на Flask и SQLite. `POST /webhook` сохраняет событие и ставит задачу в свою очередь на таблице. Воркер забирает задачи, обрабатывает их заглушкой и при ошибке повторяет с паузой. Готовых очередей (Celery, RQ, Huey) нет.

## Запуск

Нужен Python 3.11+. Проект собран через uv, интерпретатор зафиксирован в `.python-version`.

```bash
uv sync
uv run flask --app app init-db
uv run flask --app app run
```

В другом терминале:

```bash
uv run flask --app app run-worker
```

`--once` обрабатывает одну задачу и выходит. Без флага воркер опрашивает таблицу раз в секунду (`--poll-interval`).

Без uv, из уже сгенерированного `requirements.txt`:

```bash
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/flask --app app init-db
.venv/bin/flask --app app run
```

`requirements.txt` не правят руками. Его заново собирает `uv export --no-hashes --no-emit-project -o requirements.txt`. Прямые зависимости только Flask и pytest (pytest в dev-группе). Остальное в файле — их транзитивные пакеты.

Переменные окружения:

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `DATABASE` | `instance/events.db` | Файл SQLite |
| `FAIL_RATE` | `0.2` | Вероятность, с которой заглушка сама падает |

Пример:

```bash
curl -s -H 'Content-Type: application/json' \
  -d '{"event_id":"abc-123","type":"payment_succeeded","payload":{"amount":10}}' \
  http://127.0.0.1:5000/webhook

curl -s http://127.0.0.1:5000/stats
```

Повтор с тем же `event_id` тоже отвечает 200, но с `"status": "duplicate"`. Некорректное тело — 400 и `{"error": "..."}`.

Запросы лежат в коллекции Bruno: каталог `bruno/`, окружение `local` (`http://127.0.0.1:5000`). Сначала `webhook`, потом `webhook duplicate`.

## Тесты

```bash
uv run pytest -q
```

Часы в тестах подменены, ничего не спит. Обработчик тоже подменён: падения задаются флагом, а не случайностью.

1. Повторный webhook с тем же `event_id` оставляет одну строку в `events` и одну задачу. Оба ответа 200. Чужой payload повтор не перезаписывает.
2. Не JSON, нет `event_id`, пустой `event_id`, нет `payload`, `payload` не объект, тело-массив — всё это 400.
3. Успешная обработка переводит задачу в `success`.
4. Три падения подряд: `failed`, `attempts == 3`, дальше `process_once` её не берёт.
5. После первой ошибки задача не берётся до `next_run_at`. Когда срок наступил, берётся, и следующая пауза уже длиннее (2 секунды, потом 4).
6. Пока аренда не истекла, задачу «умершего» воркера никто не берёт. После истечения её забирает следующий проход.
7. `GET /stats` считает события по типам и задачи по всем четырём статусам, включая нули.

Отдельная проверка сверх списка: три потерянные аренды подряд заканчиваются `failed`, и задача не остаётся в `pending`.

## Решения и почему

- Оба ответа webhook — 200. В задании код 200 назван для повтора, а тест требует 200 и на первый запрос тоже. Отличить их можно по полю `status`: `queued` или `duplicate`. Отдельный 201 только запутал бы эту проверку.
- `events.event_id` уникален. Вставка — `INSERT ... ON CONFLICT (event_id) DO NOTHING`. Если строка реально вставилась (`rowcount == 1`), в той же транзакции `BEGIN IMMEDIATE` создаётся задача. Повтор не создаёт вторую задачу и не меняет уже сохранённый payload: иначе повторный webhook стал бы правкой истории.
- Тело должно быть JSON-объектом, `event_id` и `type` — непустыми строками, `payload` — объектом. Пробелы по краям снимаются, строка из одних пробелов считается пустой. Иначе 400 и понятный `error`. Неизвестный `type` это не ошибка приёма: событие сохраняется, а воркер ставит задаче `skipped`. Иначе новое событие терялось бы только из-за того, что обработчик ещё не написан.
- Задача захватывается в `BEGIN IMMEDIATE`: статус `pending`, `next_run_at` уже наступил, `locked_until` пустой или меньше `now`. Захвату ставится `locked_until = now + 30`. Пока аренда жива, второй воркер эту строку не видит.
- Ошибка обработки: `attempts += 1`. Пока попыток меньше 3, задача снова `pending`, `locked_until` сбрасывается, `next_run_at = now + 2**attempts` секунд. После третьей — `failed`, и выборка её больше не находит. Пауза растёт: 2 секунды, затем 4.
- Упавший процесс не снимает аренду сам. Следующий захват видит истёкший `locked_until` и считает эту попытку потраченной. На третьей такой потере задача становится `failed` с `last_error = "lease expired"`. Поэтому `pending` конечен в любом сценарии: успех, пропуск, ошибка обработчика или умерший воркер.
- Время везде — unix-секунды. `process_once(now)` принимает его аргументом, приём webhook берёт его из `CLOCK` в конфиге. Тесты подставляют свои часы и не ждут настоящие паузы.
- В тестах падение детерминировано: в конфиг кладётся другой `EVENT_HANDLER`. Боевая заглушка для `payment_succeeded`, `payment_failed` и `user_registered` пишет в лог и с вероятностью `FAIL_RATE` бросает ошибку. `FAIL_RATE=0` отключает случайность, это удобно для ручной проверки.
- Включён WAL. Веб и воркер — два процесса, и без WAL они чаще упираются в блокировку одного файла.

## Что упростил или не успел

- Воркер узнаёт о новой задаче только опросом таблицы. Отдельного сигнала «пора проснуться» нет.
- `failed` никто не перекладывает в dead-letter и не возвращает в очередь руками. После трёх попыток задача просто лежит.
- Старые события и задачи не чистятся.
- `payload` хранится текстом JSON. Отдельной схемы полей для каждого `type` нет.
- Доставка at-least-once. Если воркер сделал работу и умер до `complete`, следующий запуск сделает её снова. Заглушка только пишет в лог, поэтому повтор безвреден. Настоящему обработчику с побочным эффектом нужна была бы своя идемпотентность.
- Отдельной обработки SIGTERM нет. Процесс просто завершается, задача остаётся под арендой, и её заберёт следующий воркер, когда аренда истечёт.
